Software architecture principle
Software architecture principle
The software stack should be built around interfaces, not loyalty to specific apps.
That means Vaila should not be hardwired to:
LM Studio forever
PyCharm forever
local JSONL forever
one machine forever
one UI forever
Instead, the architecture should say:
Vaila needs an LLM provider.
Vaila needs a memory store.
Vaila needs a model registry.
Vaila needs a tool registry.
Vaila needs a UI.
Vaila needs sync.
Vaila needs logs.
Then each phase chooses the simplest software that can satisfy those needs.
The clean architecture target
Long term, the software should look like this:
Clients

 Logs


Device Layer

 Mobile client

 Level 2 Jane cores
 Level 3 platforms


The important move is making sure no tool owns the soul of the system.
LM Studio is a provider.
PyCharm is an editor.
GitHub is version history.
SQLite is storage.
FastAPI is the service layer.
Flutter is a future client.
LangGraph is a possible workflow engine.
LlamaIndex is a possible document/RAG layer.
Vaila should sit above them.
That is how you keep the project portable, expandable, and sane.

Keep LM Studio for Phase 1
LM Studio is a good fit right now because it provides local model hosting through REST APIs, Python/JS SDKs, and OpenAI-compatible endpoints. It can serve models locally or over the network, which fits the current laptop and desktop testing pattern.
Use LM Studio for:
local model testing
model comparison
OpenAI-compatible endpoint
laptop and desktop model serving
manual experimentation
Add a provider abstraction now
Even while using LM Studio, the code should call an internal interface like:
LLMProvider
Not:
LMStudioForeverClient
Reason:
Ollama also supports OpenAI-compatible APIs, including OpenAI-style chat and tool usage through its compatibility layer, so later you may want to support both LM Studio and Ollama behind the same interface.
Phase 1 provider concept:
llm_client.py
 LMStudioProvider
 future OllamaProvider
 future OpenAIProvider
Do not build all providers now. Just design so the current provider can be swapped later.
Data format
Use:
Markdown for foundation context
YAML for persona configuration
JSON for model profiles and machine profiles
JSONL for early memory
This is correct for Phase 1 because everything remains readable and editable.
Add Pydantic once schemas stabilize
Pydantic uses Python type hints for validation and serialization, which makes it useful once the memory records, route plans, model profiles, and tool definitions need stricter structure.
Good Phase 1 use:
MemoryRecord
RoutePlan
ModelProfile
PersonaManifest
MachineProfile
Do not add Pydantic too early if it slows you down. Add it when mistakes in JSON/YAML begin costing time.
Add pytest soon
Your router and memory system need regression tests. pytest is a good fit because it supports small readable tests and can scale to more complex functional tests later.
Phase 1 tests should cover:
router chooses correct task type
router chooses correct persona
weak matches default correctly
memory scope prevents persona bleed
model profile resolves correctly
fallback logic works
context packet includes foundation context

Add FastAPI
Phase 2 is the right time to start turning the core into a local service.
FastAPI is a Python web framework for building APIs using standard Python type hints, which fits a local Vaila service that other clients can call.
Use FastAPI for:
local Vaila API
chat endpoint
memory search endpoint
file analysis endpoint
tool execution endpoint
model profile endpoint
health check endpoint
This changes the architecture from:
Run main.py in terminal.
to:
Run Vaila as a local service.
Other interfaces talk to it.
That is a big step toward Home Jane.
Add SQLite
Phase 2 is also where JSONL may start feeling limited.
SQLite is built into Python through the sqlite3 module, which provides a DB-API interface for SQLite databases.
Use SQLite for:
memory records
decision logs
test results
session summaries
tool runs
agent run history later
approval queue
Do not immediately delete JSONL. Transition gently:
Phase 1:
JSONL source files


Phase 2:
SQLite working database


Migration:
import JSONL into SQLite
export SQLite memories back to JSONL or Markdown for backup
That gives you database power without losing human-readable backups.

Vector storage decision
Do not rush this.
For Phase 2, the progression should be:
SQLite keyword and tag search first
then embeddings
then vector database if needed
If you need local vector search, Chroma is simple and provides embedding storage, metadata filtering, dense and sparse search, and retrieval features. Qdrant is stronger for a more service-like vector search layer and provides vector and semantic search with HTTP and gRPC interfaces.
Recommendation:
Early Phase 2:
SQLite only


Late Phase 2:
Chroma if you want the simplest local embedding store


Phase 3 or 4:
Qdrant if retrieval becomes a serious always-on service

When to consider LangGraph
LangGraph is designed for long-running, stateful workflows and agents, and its docs emphasize controllable workflow infrastructure rather than hiding your architecture. That makes it a good candidate when your handmade workflow engine becomes too limited.
Use LangGraph when you need:
multi-step agent workflows
branching
loops
persistent agent state
interrupts and approvals
workflow recovery
Do not use it just because “agents.”
When to consider LlamaIndex
LlamaIndex is designed around data and context augmentation for LLM applications, including RAG pipelines and document-oriented workflows. It becomes useful if file analysis, document indexing, and retrieval become central.
Use LlamaIndex when you need:
document indexing
retrieval pipelines
query engines
file connectors
structured document workflows
But do not use both LangGraph and LlamaIndex at full depth immediately.
Suggested order:
First:
custom simple workflows


Then:
LlamaIndex for document retrieval if needed


Then:
LangGraph for agent orchestration if needed
Add GitHub Actions
Once tests exist, GitHub Actions should run them automatically on pushes or pull requests. GitHub Actions is built for automating build, test, and deployment workflows from a repository.
Use it for:

prevent broken commits

Docker decision
Docker helps package and run applications in containers, which becomes useful when Vaila has multiple services like API, database, vector store, and tool workers.
Do not force Docker in Phase 1.
Consider Docker in Phase 3 when you have:
FastAPI service

Mobile app decision
For a serious cross-platform app, Flutter is a strong candidate because it supports building mobile, web, desktop, and embedded apps from a single codebase.
Recommendation:
Phase 4 mobile client:
Flutter


Not:
Kivy, unless you want to stay Python-only for quick prototypes.
Kivy can build Python apps across desktop and mobile platforms, but Flutter is likely the better long-term mobile app path because Android, iOS, desktop, and web are first-class targets in its ecosystem.
Secure connection
Use a private network/VPN approach for Home Jane access instead of exposing the server raw to the internet.
Candidates:
Tailscale
WireGuard
Tailscale positions itself as identity-based secure connectivity and provides stable device-to-device networking across locations, while WireGuard is a simple, modern VPN protocol focused on secure tunnels.
Recommendation:
Beginner-friendly:
Tailscale


More manual/control-oriented:
WireGuard
For you, likely start with Tailscale later unless you specifically want the WireGuard learning path.
